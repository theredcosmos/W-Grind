LRU Cache (HashMap + linked list)

Keep a HashMap for O(1) lookup and a doubly linked list for order. Newest item sits at the front. When full, drop the item at the back.

    Understand the design

    Requirements

    Functional
    • get(key) returns the value or -1
    • put(key, value) inserts or updates
    • When full, remove the least recently used key
    Non-functional
    • get and put in O(1)
    • Thread-safe if shared across requests
    • Capacity fixed at creation

    Core objects (nouns become classes)

    • LRUCache: the public API: get, put, capacity
    • Node: one entry: key, value, prev, next
    • HashMap<K, Node>: jump straight to a node in O(1)

    Concurrency: what can go wrong with many threads

    Two threads calling put at the same time can corrupt prev/next pointers. Simple fix: mark get and put synchronized. Faster: ReentrantReadWriteLock does not help much because get also moves nodes, so it is a write. In real projects use Caffeine or LinkedHashMap wrapped with Collections.synchronizedMap.

    LRUCache.java (HashMap + doubly linked list)
    class LRUCache {
    private class Node {
        int key, value;
        Node prev, next;
        Node(int k, int v) { key = k; value = v; }
    }

    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);   // dummy: most recent after this
    private final Node tail = new Node(0, 0);   // dummy: least recent before this

    LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public synchronized int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        remove(n);          // take it out of its place
        addFirst(n);        // put it at the front: just used
        return n.value;
    }

    public synchronized void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) {                // update existing
            n.value = value;
            remove(n);
            addFirst(n);
            return;
        }
        if (map.size() == capacity) {   // full: evict least recent
            Node lru = tail.prev;
            remove(lru);
            map.remove(lru.key);
        }
        Node fresh = new Node(key, value);
        addFirst(fresh);
        map.put(key, fresh);
    }

    private void remove(Node n) {
        n.prev.next = n.next;
        n.next.prev = n.prev;
    }

    private void addFirst(Node n) {
        n.next = head.next;
        n.prev = head;
        head.next.prev = n;
        head.next = n;
    }
}
    Shortcut: LinkedHashMap (say it, then build the real one)
    class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LRUCache(int capacity) {
        super(capacity, 0.75f, true);   // true = access order
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;       // evict when over capacity
    }
}

    Follow-up questions interviewers ask

    How would you add expiry (TTL)?

    Store an expiresAt in each Node. On get, if expired, remove it and return -1. Optionally a background thread cleans up expired nodes.

    How is LFU different?

    LFU evicts the key used the fewest times. Keep a map from frequency to a linked list of nodes and track the minimum frequency. Still O(1).

    How would you make it distributed?

    Use Redis with maxmemory-policy allkeys-lru, or shard keys across nodes with consistent hashing.

    Why not just a queue?

    Moving an item from the middle of a queue to the end is O(n). The linked list plus map makes it O(1).

    Common mistakes

    Forgetting to remove from the map

    When you evict the tail node you must also call map.remove(lru.key), or the map grows forever.

    Singly linked list

    Without prev you cannot unlink a node in O(1).

    Not moving on get

    A get is also a use. Forgetting to move the node makes it LRU on writes only.

    Null checks everywhere

    Use dummy head and tail nodes and the code becomes four simple lines.

    Simple LRU

    Dummy head and tail remove all null checks.

    class LRUCache {
    class Node { int key, val; Node prev, next; }
    Map<Integer, Node> map = new HashMap<>();
    Node head = new Node(), tail = new Node();   // dummy ends
    int cap;
    LRUCache(int cap) { this.cap = cap; head.next = tail; tail.prev = head; }

    int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        remove(n); addFront(n);              // now most recent
        return n.val;
    }
    void put(int key, int val) {
        Node n = map.get(key);
        if (n != null) { n.val = val; remove(n); addFront(n); return; }
        if (map.size() == cap) {             // full: evict least recent
            Node last = tail.prev;
            remove(last); map.remove(last.key);
        }
        n = new Node(); n.key = key; n.val = val;
        map.put(key, n); addFront(n);
    }
    void remove(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    void addFront(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
}

    Say this in the interview

    Why two structures?

    HashMap alone finds fast but has no order. A list alone has order but finds slowly. Together both are O(1).

    Not thread-safe

    Wrap calls in synchronized or use a lock. Mention this and offer to add it.

      Board, Player, Game
      enum GameStatus { IN_PROGRESS, WIN, DRAW }

record Player(String name, char symbol) {}

class Board {
    private final int n;
    private final char[][] cells;
    private final int[] rows, cols;
    private int diag, anti, filled;

    Board(int n) {
        this.n = n;
        cells = new char[n][n];
        rows = new int[n];
        cols = new int[n];
    }

    /** returns true if this move wins */
    boolean place(int r, int c, char symbol) {
        if (r < 0 || c < 0 || r >= n || c >= n || cells[r][c] != 0)
            throw new IllegalArgumentException("Invalid move");
        cells[r][c] = symbol;
        filled++;
        int add = symbol == 'X' ? 1 : -1;
        rows[r] += add;
        cols[c] += add;
        if (r == c) diag += add;
        if (r + c == n - 1) anti += add;
        return Math.abs(rows[r]) == n || Math.abs(cols[c]) == n
            || Math.abs(diag) == n || Math.abs(anti) == n;
    }

    boolean isFull() { return filled == n * n; }
}

class Game {
    private final Board board = new Board(3);
    private final Player[] players;
    private int turn = 0;
    private GameStatus status = GameStatus.IN_PROGRESS;

    Game(Player a, Player b) { players = new Player[]{a, b}; }

    GameStatus play(int r, int c) {
        if (status != GameStatus.IN_PROGRESS) throw new IllegalStateException("Game over");
        Player p = players[turn];
        if (board.place(r, c, p.symbol())) status = GameStatus.WIN;
        else if (board.isFull()) status = GameStatus.DRAW;
        else turn = 1 - turn;            // next player
        return status;
    }
}

      Follow-up questions interviewers ask

      How do you support N x N?

      Board already takes n. The counter arrays scale with n and the check stays O(1).

      How do you add a computer player?

      Make Player an interface with nextMove(Board). HumanPlayer reads input; ComputerPlayer picks a move (random or minimax). Strategy pattern.

      Undo a move?

      Keep a stack of moves. Undo pops the last move and reverses the counter changes.

      How would you save and resume?

      Store the move list. Replaying the moves rebuilds the board.

      Common mistakes

      Scanning the whole board after each move

      It works, but the counter trick is the answer interviewers hope for.

      Game class doing everything

      Keep win logic in Board so Game stays small.

      Not validating moves

      Out-of-range and taken cells must be rejected.

      Using strings for status

      Use an enum.

class HasMoneyState implements State {
    public void insertCoin(VendingMachine m, int amount) { m.addCredit(amount); }

    public void select(VendingMachine m, String code) {
        int price = m.inventory().price(code);
        if (!m.inventory().inStock(code)) { System.out.println("Sold out"); return; }
        if (m.credit() < price) { System.out.println("Need " + (price - m.credit()) + " more"); return; }
        m.setState(new DispensingState());
        m.inventory().take(code);
        m.refund(m.credit() - price);       // change
        m.setState(new IdleState());
    }

    public void cancel(VendingMachine m) {
        m.refund(m.credit());
        m.setState(new IdleState());
    }
}

    public void insertCoin(VendingMachine m, int a) { System.out.println("Please wait"); }

class VendingMachine {
    private State state = new IdleState();
    private int credit;
    private final Inventory inventory = new Inventory();

    public synchronized void insertCoin(int a)  { state.insertCoin(this, a); }
    public synchronized void select(String c)   { state.select(this, c); }
    public synchronized void cancel()           { state.cancel(this); }

    void setState(State s) { state = s; }
    void addCredit(int a)  { credit += a; }

        Follow-up questions interviewers ask

        Add an OutOfService state?

        New class OutOfServiceState where every method prints "Out of service". No existing class changes: Open/Closed.

        Accept notes and cards?

        Introduce a PaymentMethod interface (Coin, Note, Card). The state calls payment.collect().

        How to return the fewest coins as change?

        Greedy from the largest coin down works for normal coin systems (10, 5, 2, 1).

        Both swap an object. In State the object changes itself as events happen; in Strategy the client picks it once.

class Slot {
    final String id; final Size size;
    private final AtomicBoolean taken = new AtomicBoolean(false);
    Slot(String id, Size size) { this.id = id; this.size = size; }
    boolean fits(Vehicle v) { return size.ordinal() >= v.size().ordinal(); }
    boolean tryOccupy()     { return taken.compareAndSet(false, true); }  // atomic
    void free()             { taken.set(false); }
}

record Ticket(Vehicle vehicle, Slot slot, Instant entry) {}

interface PricingStrategy { long fee(Ticket t, Instant exit); }

class HourlyPricing implements PricingStrategy {
    private final Map<Size, Long> rate = Map.of(Size.SMALL, 10L, Size.MEDIUM, 20L, Size.LARGE, 40L);
    public long fee(Ticket t, Instant exit) {
        long hours = Math.max(1, (Duration.between(t.entry(), exit).toMinutes() + 59) / 60);
        return hours * rate.get(t.slot().size);
    }
}

class ParkingLot {
    private final List<Slot> slots;
    private final PricingStrategy pricing;
    ParkingLot(List<Slot> slots, PricingStrategy pricing) { this.slots = slots; this.pricing = pricing; }

    Ticket park(Vehicle v) {
        for (Slot s : slots)
            if (s.fits(v) && s.tryOccupy())           // first fitting free slot
                return new Ticket(v, s, Instant.now());
        throw new IllegalStateException("Lot full");
    }

    long unpark(Ticket t) {
        t.slot().free();
        return pricing.fee(t, Instant.now());
    }
}

class Elevator {
    private int floor = 0;
    private Direction dir = Direction.IDLE;
    private final TreeSet<Integer> up = new TreeSet<>();
    private final TreeSet<Integer> down = new TreeSet<>();

    synchronized void addStop(int f) {
        if (f > floor) up.add(f);
        else if (f < floor) down.add(f);
        if (dir == Direction.IDLE) dir = f > floor ? Direction.UP : Direction.DOWN;
    }

    /** move one step; called by a timer or loop */
    synchronized void step() {
        if (dir == Direction.UP) {
            Integer next = up.ceiling(floor);
            if (next == null) { dir = down.isEmpty() ? Direction.IDLE : Direction.DOWN; return; }
            floor++;
            if (floor == next) { up.remove(next); openDoors(); }
        } else if (dir == Direction.DOWN) {
            Integer next = down.floor(floor);
            if (next == null) { dir = up.isEmpty() ? Direction.IDLE : Direction.UP; return; }
            floor--;
            if (floor == next) { down.remove(next); openDoors(); }
        }
    }

    int floor() { return floor; }
    Direction dir() { return dir; }
    private void openDoors() { System.out.println("Doors open at " + floor); }
}

        return cars.stream()
            .min(Comparator.comparingInt(e -> Math.abs(e.floor() - floor)))
            .orElseThrow();

}

class Group {
    private final Map<String, Long> balance = new HashMap<>();   // + means is owed, - means owes

    /** equal split: payer paid amount for everyone in 'members' */
    synchronized void addEqualExpense(String payer, long amountPaise, List<String> members) {
        long share = amountPaise / members.size();
        long leftover = amountPaise - share * members.size();     // e.g. 100 / 3 leaves 1
        for (String m : members) balance.merge(m, -share, Long::sum);
        balance.merge(payer, amountPaise - leftover, Long::sum);  // payer absorbs the leftover paise
    }

    List<Payment> simplify() {
        PriorityQueue<Map.Entry<String, Long>> creditors =
            new PriorityQueue<>((a, b) -> Long.compare(b.getValue(), a.getValue()));
        PriorityQueue<Map.Entry<String, Long>> debtors =
            new PriorityQueue<>((a, b) -> Long.compare(a.getValue(), b.getValue()));
        for (var e : balance.entrySet()) {
            if (e.getValue() > 0) creditors.add(new AbstractMap.SimpleEntry<>(e));
            if (e.getValue() < 0) debtors.add(new AbstractMap.SimpleEntry<>(e));
        }
        List<Payment> out = new ArrayList<>();
        while (!creditors.isEmpty() && !debtors.isEmpty()) {
            var c = creditors.poll(); var d = debtors.poll();
            long pay = Math.min(c.getValue(), -d.getValue());
            out.add(new Payment(d.getKey(), c.getKey(), pay));
            if (c.getValue() - pay > 0) { c.setValue(c.getValue() - pay); creditors.add(c); }
            if (d.getValue() + pay < 0) { d.setValue(d.getValue() + pay); debtors.add(d); }
        }
        return out;   // at most n - 1 payments
    }
}

record Hold(String userId, Instant expiresAt) {
    boolean expired() { return Instant.now().isAfter(expiresAt); }

class InMemorySeatLocks {
    private final ConcurrentHashMap<HoldKey, Hold> holds = new ConcurrentHashMap<>();

    /** all-or-nothing hold of several seats */
    boolean lock(String show, List<String> seats, String user, Duration ttl) {
        List<String> sorted = seats.stream().sorted().toList();   // fixed order
        List<HoldKey> taken = new ArrayList<>();
        Hold mine = new Hold(user, Instant.now().plus(ttl));
        for (String seat : sorted) {
            HoldKey k = new HoldKey(show, seat);
            holds.computeIfPresent(k, (key, h) -> h.expired() ? null : h);  // drop expired hold
            if (holds.putIfAbsent(k, mine) != null) {                         // atomic
                taken.forEach(holds::remove);                                 // roll back
                return false;
            }
            taken.add(k);
        }
        return true;
    }

    void unlock(String show, List<String> seats, String user) {
        for (String s : seats) holds.computeIfPresent(new HoldKey(show, s),
            (k, h) -> h.userId().equals(user) ? null : h);
    }
}

class BookingService {
    private final InMemorySeatLocks locks = new InMemorySeatLocks();

    boolean hold(String show, List<String> seats, String user) {
        return locks.lock(show, seats, user, Duration.ofMinutes(10));
    }

    void confirm(String show, List<String> seats, String user, String paymentId) {
        // INSERT INTO booking_seats(show_id, seat_id, ...)  -- UNIQUE(show_id, seat_id)
        locks.unlock(show, seats, user);
    }
}

                        What does volatile do?

                        Makes writes visible to other threads immediately, but does not make count++ atomic.

                          2. How an index makes a query fast

                          Without an index the database reads every row (full scan). A B-tree index is like a phone book: jump to the right page in a few hops.

                          B-tree index pages
                          table rows (ids), read one by one in a full scan
                          Pick an id and compare. Watch the "rows touched" count.
                          How it works
                          1. The B-tree keeps keys sorted in pages. Each page points to child pages for smaller and bigger ranges.
                          2. To find 61: look at the root, go to the child for 50-74, then the leaf. 3 page reads instead of 27 rows.
                          3. For 1 billion rows a B-tree is only about 4 levels deep. That is why indexed lookups take milliseconds.
                          Trade-offs and mistakes
                          • Writes get slower: every insert must update every index on the table.
                          • More storage: each index is a copy of the column plus pointers.
                          • Composite index order matters: an index on (city, age) helps WHERE city=? and WHERE city=? AND age=?, not WHERE age=? alone.
                          • Functions on columns break indexes: WHERE LOWER(email)=? cannot use a plain index on email.
                          • Low-cardinality columns (gender, boolean) rarely benefit.
                          I add an index on (user_id, created_at) because the feed query is "latest posts by user". Writes get a bit slower, which is fine for this read-heavy system.

                          3. ACID, shown with a bank transfer

                          Transfer 100 from Asha to Ravi. Two steps: take 100 from Asha, give 100 to Ravi. What if the server crashes in between?

                          Press a button.

                          A: Atomicity

                          All steps happen, or none. A crash rolls back the half-done transfer.

                          C: Consistency

                          Rules always hold: balance never negative, total money unchanged.

                          I: Isolation

                          Two transfers at the same time do not see each other's half-done work.

                          D: Durability

                          Once committed, it survives a crash (written to the disk log first).

                          4. Isolation levels: what can go wrong with two transactions

                          Two transactions run at the same time. Weaker isolation is faster but allows strange results called anomalies. Pick an anomaly and play it.

                          How to fix lost updates in real code
                          • Atomic update: UPDATE account SET bal = bal - 100 WHERE id = 1 AND bal >= 100. The database does read and write in one step.
                          • Pessimistic lock: SELECT ... FOR UPDATE locks the row until commit. Simple, but others wait.
                          • Optimistic lock: add a version column. UPDATE ... SET version = 6 WHERE id = 1 AND version = 5. If 0 rows changed, someone else won: reload and retry. In JPA this is @Version.

                          5. Normalize or denormalize?

                          Normalized = each fact stored once (no duplicates, needs JOINs). Denormalized = copy data where you read it (fast reads, harder updates).

                          Switch tabs and press the buttons to compare.
                          When to use which
                          • Normalize for write-heavy, correctness-critical data: banking, orders, inventory (your core banking work is normalized).
                          • Denormalize for read-heavy views: feeds, product pages, dashboards. Often a separate read model built from events (CQRS).
                          • NoSQL designs are usually denormalized: you design the table around the query.

                          6. Read replicas and replication lag

                          One primary takes all writes. Copies (replicas) receive changes and serve reads. Great for read-heavy apps, but replicas can be a little behind.

                          Press a button to see replication lag.
                          Trade-offs and interview answer
                          • Async replication (default): fast writes, replicas may lag by milliseconds to seconds. If the primary dies, last writes can be lost.
                          • Sync replication: no data loss, but every write waits for the replica.
                          • Read-your-writes fix: for a few seconds after a user writes, send that user's reads to the primary (or track the write position).
                          • Failover: if the primary dies, promote a replica. Watch out for split brain (two primaries).
                          Reads are 100x writes, so I add 3 read replicas. To avoid users not seeing their own new post, I read from the primary for that user for 5 seconds after a write.

                          CAP theorem: what happens when the network breaks

                          Data is copied on two servers. If the cable between them breaks (a partition), you must choose: refuse requests to stay correct (CP), or answer with maybe-old data to stay up (AP).

                          Break the network, write on A, then read on B. Try both modes.
                          How it works and PACELC

                          Partitions will happen in any distributed system, so P is not optional. The real choice is C or A during a partition.

                          PACELC adds the normal case: Else (no partition), choose Latency or Consistency. Waiting for all replicas to agree is consistent but slower.

                          SystemDuring partitionNormal times
                          Bank ledger, PostgreSQL primaryCPConsistency
                          Cassandra, DynamoDB (default)APLatency

                          Interview answer and mistakes
                          For the wallet balance I choose CP: better to show an error than a wrong balance. For the like counter I choose AP: a slightly old count is fine and the app stays up.
                          • Mistake: saying "we pick CA". No partition tolerance means a single machine.
                          • Mistake: one choice for the whole system. Different data can make different choices.

                          Consistency models: when will others see my write?

                          After you update something, how soon do readers see it? Play each model.

                          Where each is used
                          • Strong: every read sees the latest write. Bank balance, inventory count at checkout, seat booking.
                          • Eventual: replicas agree "soon" (ms to seconds). Likes, views, follower counts, DNS.
                          • Read-your-writes: you always see your own changes, others may lag. Profile edits, your own posts.
                          • Monotonic reads: you never see time go backwards (sticky to one replica).

                          Latency vs throughput

                          Latency = how long one request takes (one car's trip time). Throughput = how many requests per second (cars per hour on the highway). More lanes raise throughput but do not make one trip faster.

                          Percentiles: why p99 matters more than average

                          p50 = half the requests are faster. p99 = 99 out of 100 are faster. If a page calls 10 services, the chance that at least one hits its slow p99 is about 10%. That is why big companies track p99 and p999.

                          Our target is p99 under 200 ms for the feed API, measured at the load balancer.

                            Load balancing and hash ring

                            A load balancer spreads requests over servers. A consistent hash ring decides which server owns a key, and moves very few keys when servers come and go.

                            24 keys sit on a circle. Each key belongs to the next node clockwise.

                            Caching strategies

                            A cache keeps popular data in fast memory. The two questions: how do writes reach the cache, and what do you throw out when it is full.

                            Write strategies

                            Cache-aside

                            App reads cache first. On a miss it reads the database and fills the cache.

                            Good for

                            Most apps. Simple and safe.

                            Write-through

                            Every write goes to cache and database together.

                            Good for

                            Data that must be fresh. Slower writes.

                            Write-back

                            Write to cache first, flush to database later.

                            Good for

                            Heavy writes. Risk of data loss if cache dies.

                            Write-around

                            Write to database only. Cache fills on the next read.

                            Good for

                            Data written once and rarely read.

                            Eviction: LRU vs LFU (cache size 3)

                            LRU drops the item unused for the longest time. LFU drops the item used the fewest times.

                            Remember

                            • Set a TTL on cached items so stale data expires on its own.
                            • Cache stampede: many requests miss at once and hit the database. Fix with locking or early refresh.
                            • Invalidation is the hard part: delete the key on update rather than trying to patch it.
                            • Redis: in-memory, rich types, optional persistence. CDN: caches static files near the user.

                            In an interview say

                            "I would use cache-aside with a TTL and LRU eviction, and delete the key on writes. I would watch the hit rate."

                            Go deeper

                            How it works, step by step
                            1Read: check cache first
                            2Miss: load from DB
                            3Store in cache with TTL
                            4On update: write DB, then delete the cache key
                            Real-world example

                            Product pages on Flipkart-style sites are cache-aside in Redis with a TTL; prices are invalidated on change. Sessions and carts often live only in Redis.

                            Trade-offs
                            • Cache-aside: simple, cache only holds what is read, but the first read is slow.
                            • Write-through: cache always fresh, every write is slower.
                            • Write-back: fastest writes, risk of losing data if the cache dies.
                            • LRU suits recency (feeds); LFU suits long-term popularity (top products).
                            Common mistakes
                            • Updating the cache and the DB in the wrong order, leaving stale data. Prefer: update DB, then delete the key.
                            • No TTL: stale data forever and memory fills up.
                            • Caching everything: low hit rate, wasted memory.
                            • Forgetting cache stampede on hot keys (see Bottleneck finder).

                            Replication, sharding, quorum

                            Copy data for safety and read speed (replication). Split data for size and write speed (sharding). Quorum rules decide how sure a read is.

                            Replication and failover

                            Async replication is fast but followers lag. If the leader dies before copying, those writes are lost.

                            Sharding strategies

                            Three shards. Range is easy to query but can make hot spots. Hash is even. Directory is flexible but needs a lookup service.

                            Quorum: N, R, W

                            If R + W is bigger than N, a read always touches at least one copy with the newest value.

                            CAP in one table

                            When the network splitsCP systemAP system
                            BehaviourRefuses some requests to stay correctAnswers every request, may be stale
                            ExamplesHBase, etcd, ZooKeeper, bank ledgerCassandra, DynamoDB (default), DNS
                            Use forPayments, inventory countsFeeds, likes, carts

                            Remember

                            • Pick a shard key with many values and even traffic. Bad key (country, date) means a hot shard.
                            • Cross-shard joins and transactions are painful, so design queries around the shard key.
                            • Replication lag: after a write, read from the leader (or same session) if the user must see it.

                            In an interview say

                            "I would replicate for availability and read scaling, shard by user id with hashing once one database cannot hold the writes, and use quorum reads only where I need strong consistency."

                            Go deeper

                            How it works, step by step
                            1Writes go to the leader
                            2Leader streams changes to followers
                            3Data is split into shards by a key
                            4Quorum: write to W nodes, read from R nodes; if R + W > N you read the latest
                            Real-world example

                            Cassandra with N=3, W=QUORUM(2), R=QUORUM(2) gives strong reads per key. A bank's core ledger instead uses one primary with a synchronous standby.

                            Trade-offs
                            • Range sharding keeps ranges together (good for scans) but creates hot shards (all new orders on the last shard).
                            • Hash sharding spreads load evenly but range queries hit every shard.
                            • Directory sharding is flexible but the directory becomes a critical service.
                            • Higher W or R = more consistent but slower and less available.
                            Common mistakes
                            • Sharding by a low-cardinality key (country): one shard gets India.
                            • Cross-shard joins and transactions everywhere: pick a key that keeps related data together (shard orders by customer_id).
                            • Forgetting resharding: plan with consistent hashing or many logical shards mapped to fewer machines.

                            Rate limiting

                            A rate limiter says no when a client sends too many requests. Two common ways: token bucket and sliding window.

                            Try both with the same traffic

                            Token bucket: capacity 5, refills 1 token per second. Sliding window: at most 5 requests in any 10 seconds.

                            Remember

                            • Token bucket allows short bursts, then a steady rate. Good default.
                            • Fixed window is simplest but allows a double burst at the window edge. Sliding window avoids this.
                            • In a cluster, keep counters in Redis (atomic INCR with expiry, or a Lua script).
                            • Return HTTP 429 with a Retry-After header. Limit by user id, API key or IP.

                            In an interview say

                            "I would use a token bucket per user stored in Redis, enforced at the API gateway, returning 429 with Retry-After."

                            Go deeper

                            How it works, step by step
                            1Identify the caller (user id, API key, IP)
                            2Look up its counter or bucket in Redis
                            3Allow if under the limit, else return 429
                            4Send headers: limit, remaining, retry-after
                            Real-world example

                            Login endpoints allow ~5 attempts per minute per account; public APIs like GitHub give 5,000 requests per hour per token and return 429 with Retry-After.

                            Trade-offs
                            • Token bucket allows short bursts and is easy to explain.
                            • Fixed window is simplest but allows 2x bursts at the window edge.
                            • Sliding window log is exact but stores every timestamp; sliding window counter approximates it cheaply.
                            • Central Redis counter = accurate across servers but adds a network hop; local limits are fast but approximate.
                            Common mistakes
                            • Limiting only by IP: many users share an office or mobile carrier IP.
                            • Not making the Redis check atomic (use INCR + EXPIRE or a Lua script).
                            • Returning 500 instead of 429 so clients retry immediately.

                            Queues and Kafka

                            A queue lets one part hand work to another without waiting. Kafka splits a topic into partitions; each partition is read by one consumer in a group.

                            Partitions and consumer group

                            Same key always lands in the same partition, so order per key is kept. More consumers than partitions means idle consumers.

                            Remember

                            • Order is guaranteed inside a partition only, not across the topic.
                            • Delivery: at-most-once (may lose), at-least-once (may repeat, so make consumers idempotent), exactly-once (costly).
                            • Use a queue to smooth traffic spikes, run slow jobs (email, video), and decouple services.
                            • Dead-letter queue: park messages that keep failing so they do not block others.

                            In an interview say

                            "I would put slow work on Kafka keyed by order id, run a consumer group, and make the consumer idempotent because delivery is at-least-once."

                            Go deeper

                            How it works, step by step
                            1Producer sends a message with a key
                            2Key decides the partition (same key, same partition, same order)
                            3Messages are appended to the partition log and kept for days
                            4Each consumer in a group owns some partitions and commits its offset
                            Real-world example

                            An e-commerce OrderPlaced topic with 12 partitions keyed by order_id: payment, email and analytics are separate consumer groups, each reading every message at its own pace.

                            Trade-offs
                            • More partitions = more parallel consumers, but ordering is only within a partition.
                            • Kafka keeps messages (replay is possible); RabbitMQ deletes after ack but has richer routing.
                            • At-least-once delivery is the default: consumers must be idempotent.
                            Common mistakes
                            • More consumers than partitions: the extra ones sit idle.
                            • Using a random key when order matters (all events of one order must share a key).
                            • No dead-letter topic: one bad message blocks the partition forever.
                            • Committing the offset before processing: a crash loses the message.

                            Resilience and reliability

                            Things fail all the time. Stop calling a dead service, retry politely, make repeats safe, and undo half-finished work.

                            Circuit breaker

                            3 failures in a row open the circuit. After 5 seconds one trial call decides.

                            Retry with backoff and jitter

                            Wait longer each time (1s, 2s, 4s...). Jitter stops all clients retrying at the same moment.

                            Idempotency key

                            A retry after a timeout must not charge twice.

                            Saga: undo with compensation

                            No big database transaction across services. Each step has an undo step instead.

                            Remember

                            • Always set timeouts on remote calls. No timeout means threads pile up and the caller dies too.
                            • Idempotency key: client sends a unique id, server stores the result and returns it on repeats.
                            • Saga: choreography (events) or orchestration (a coordinator). Orchestration is easier to follow.
                            • Bulkhead: separate thread pools per dependency so one slow service cannot use all threads.

                            In an interview say

                            "Every remote call has a timeout, retries with exponential backoff and jitter, and a circuit breaker. Payment calls carry an idempotency key. Multi-service flows use a saga."

                            Go deeper

                            How it works, step by step
                            1Set a timeout on every remote call
                            2Retry only safe operations, with backoff and jitter
                            3Open the circuit after many failures; fail fast with a fallback
                            4Use idempotency keys so retries never double-charge
                            5For multi-service workflows, use a saga with compensating steps
                            Real-world example

                            UPI and card payments send an idempotency key (transaction reference) with every request. If the response is lost and the app retries, the bank returns the first result instead of charging twice.

                            Trade-offs
                            • Retries improve success but multiply load during outages.
                            • Circuit breakers protect the system but users see fallbacks or errors sooner.
                            • Sagas avoid distributed locks but the system is briefly inconsistent and you must write undo logic.
                            Common mistakes
                            • No timeout: threads pile up waiting forever and the caller dies too.
                            • Retrying non-idempotent POSTs without a key.
                            • Using two-phase commit across microservices (slow, fragile) instead of a saga.

                            What happens when you type a URL

                            This is the classic question. Walk the request from browser to database and back, naming each building block.

                            Step through

                            Polling vs long polling vs SSE vs WebSocket

                            Server events happen at seconds 3, 6.5 and 9. How fast does the client learn, and how many requests does it cost?

                            Remember

                            • Polling: simplest, wasteful. SSE: server to client only, auto-reconnects, works over plain HTTP. WebSocket: two-way, good for chat and games.
                            • Use WebSocket when the client also sends often. Use SSE for notifications and live feeds.
                            • At scale, WebSocket servers hold open connections, so you need sticky routing or a pub/sub layer between servers.

                            In an interview say

                            "For notifications I would use SSE or WebSocket behind the load balancer, with Redis pub/sub to fan messages out between servers."

                            Go deeper

                            How it works, step by step
                            1Browser cache, then DNS lookup
                            2TCP + TLS handshake
                            3HTTP request travels via CDN / load balancer
                            4Server runs code, queries cache/DB
                            5Response returns; browser parses HTML, loads CSS/JS/images, renders
                            Real-world example

                            Typing your bank's URL: DNS returns the CDN edge, TLS proves the certificate, the WAF and load balancer forward to the web tier, which calls core banking services, then the page renders.

                            Trade-offs
                            • Each step can be cached: browser cache, DNS cache, CDN cache, app cache.
                            • HTTP/2 and keep-alive reuse connections so the handshake happens once.
                            Common mistakes
                            • Forgetting DNS and TLS entirely.
                            • Not mentioning caching at each layer.
                            • Going too deep into one layer (TCP flags) and never finishing the journey.

                            API design and pagination

                            A good API is predictable: nouns in URLs, verbs in HTTP methods, and safe paging for long lists.

                            Offset vs cursor pagination

                            Newest first, 4 per page. Watch what happens to the repeated item when new data arrives.

                            REST cheat table

                            ActionRequestSuccess
                            List ordersGET /orders?limit=20&cursor=abc200
                            Get oneGET /orders/42200, 404 if missing
                            CreatePOST /orders (+ Idempotency-Key)201 + Location
                            ReplacePUT /orders/42200
                            Change a fieldPATCH /orders/42200
                            DeleteDELETE /orders/42204

                            Remember

                            • Offset is easy but slow on deep pages (database skips rows) and can repeat or skip items. Cursor is fast and stable.
                            • Status codes: 400 bad input, 401 not logged in, 403 not allowed, 404 missing, 409 conflict, 429 too many, 5xx server fault.
                            • Version the API (/v1/) and never break existing fields.
                            • PUT, DELETE and GET are idempotent. POST is not, unless you add a key.

                            In an interview say

                            "I would use cursor pagination for feeds, versioned REST endpoints, and idempotency keys on POST."

                            Go deeper

                            How it works, step by step
                            1Name resources as nouns: /users/42/orders
                            2Use the right method: GET read, POST create, PUT replace, PATCH update, DELETE
                            3Return proper status codes
                            4Paginate lists with a cursor
                            5Version the API: /v1/
                            Real-world example

                            Twitter, Slack and Stripe all use cursor pagination: the response carries next_cursor, and the client sends it back to get the next page, so new items do not shift pages.

                            Trade-offs
                            • Offset is simple and allows jumping to page 50, but gets slow on big tables and skips or repeats items when data changes.
                            • Cursor is fast and stable, but you cannot jump to an arbitrary page.
                            • REST is simple and cacheable; gRPC is faster between services; GraphQL lets clients pick fields.
                            Common mistakes
                            • Verbs in URLs (/getUser).
                            • Returning 200 with an error message inside.
                            • Unbounded lists with no pagination.
                            • Breaking changes without a new version.

                            News feed fan-out

                            When someone posts, do you push it into every follower feed now, or let followers pull it when they open the app? Celebrities break the push model.

                            Compare the costs

                            Assume every user follows 200 accounts. Hybrid pushes for normal users and pulls for celebrities (above 10,000 followers).

                            Remember

                            • Push (fan-out on write): fast reads, expensive writes, wasted work for inactive users.
                            • Pull (fan-out on read): cheap writes, slow reads that need many queries.
                            • Hybrid: push for most, pull and merge for celebrity posts. This is what big feeds do.
                            • Store each feed as a Redis list of post ids. Fetch post bodies in one batch.

                            In an interview say

                            "I would use hybrid fan-out: push into follower feed lists through a queue, but skip celebrities and merge their recent posts at read time."

                            Go deeper

                            How it works, step by step
                            1User posts
                            2Push model: write the post id into every follower's feed list
                            3Pull model: at read time, fetch recent posts of everyone you follow and merge
                            4Hybrid: push for normal users, pull for celebrities
                            Real-world example

                            Instagram and Twitter use the hybrid: most posts are pushed into followers' Redis feed lists, while posts from accounts with millions of followers are merged in at read time.

                            Trade-offs
                            • Push: very fast reads, heavy writes (a celebrity post = millions of writes), wasted work for inactive followers.
                            • Pull: cheap writes, slow reads that query many users.
                            • Hybrid: best of both, more complex code.
                            Common mistakes
                            • Picking push without mentioning the celebrity problem.
                            • Storing full posts in every feed instead of just ids.
                            • Forgetting pagination of the feed itself.

                            Geohash, bloom filter, base62

                            Three small tools that appear in many designs: geohash for nearby search, bloom filter for cheap "have I seen this?", base62 for short URLs.

                            Geohash: click the map

                            Each extra character shrinks the box. Nearby places share a prefix, so a prefix search finds neighbours.

                            Bloom filter (16 bits, 3 hashes)

                            All 3 bits set means "maybe in set". Any bit empty means "definitely not". It can give false positives, never false negatives.

                            Base62 short code

                            0-9, a-z, A-Z gives 62 symbols. 7 characters give 62^7, about 3.5 trillion short links.

                            Remember

                            • Geohash edge case: two close points can have different prefixes, so also search the 8 neighbouring boxes. Quadtrees and S2 are alternatives.
                            • Use a bloom filter before a slow lookup: crawler seen-URLs, "username taken", cache penetration guard.
                            • Short URL: generate a unique id (counter or ID service), encode in base62, store id to long URL. Do not hash and truncate without handling collisions.

                            In an interview say

                            "For nearby drivers I would index locations by geohash in Redis and query the cell plus its 8 neighbours."

                            Go deeper

                            How it works, step by step
                            1Geohash: split the map into a grid, each cell gets a string; nearby places share a prefix
                            2Bloom filter: k hash functions set k bits; if any bit is 0 the item is definitely absent
                            3Base62: turn a numeric id into a short string using 0-9, a-z, A-Z
                            Real-world example

                            Uber/Ola find nearby drivers by geohash prefix (plus neighbouring cells). Browsers and databases use Bloom filters to skip lookups (Cassandra checks a Bloom filter before reading a disk file). URL shorteners turn id 125 into "21" in base62.

                            Trade-offs
                            • Geohash cells near boundaries: always search the 8 neighbouring cells too.
                            • Bloom filters give false positives (says maybe when it is no) but never false negatives; you cannot delete items from a basic one.
                            • Base62 of a counter is short and unique but predictable; add randomness if codes must be hard to guess.
                            Common mistakes
                            • Searching only the user's own geohash cell.
                            • Using a Bloom filter where a false positive is dangerous without a real check after it.
                            • Generating short codes by random strings without checking collisions.
